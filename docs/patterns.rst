Design patterns
===============

Generated by ``invariant guidelines render`` from ``docs/guidelines/patterns.yaml`` (catalogue cd9401f41ed6). Do not edit this file: change the catalogue, then render. A design names the pattern a new abstraction applies by its id, or says why none fits.

Creational patterns
-------------------

.. _gof.abstract-factory:

Abstract Factory
~~~~~~~~~~~~~~~~

One interface hands out a whole set of related objects that are meant to be used together, so a caller swaps the entire set by swapping one factory and never names the concrete types.

- Id: ``gof.abstract-factory``

Use when:

- several products must always come from the same variant
- the variant is chosen once, at the composition root

Avoid when:

- there is only one product, or only one variant
- new product kinds are added often, since every factory must grow

.. _gof.builder:

Builder
~~~~~~~

A separate object assembles a complex value step by step and hands it over only when it is complete, keeping the construction sequence apart from the value it produces.

- Id: ``gof.builder``

Use when:

- a value has many optional parts or must be validated as a whole
- the same steps produce different representations

Avoid when:

- a constructor or a literal with named arguments reads just as well

.. _gof.factory-method:

Factory Method
~~~~~~~~~~~~~~

A class leaves the choice of which concrete object to create to an overridable method, so a subclass or a supplied function decides the type while the surrounding logic stays fixed.

- Id: ``gof.factory-method``

Use when:

- shared logic needs an object whose concrete type varies by context

Avoid when:

- a plain injected instance or a function parameter would do

.. _gof.prototype:

Prototype
~~~~~~~~~

New objects are made by copying a configured example instead of constructing them from scratch, so expensive or intricate set-up is done once and reused.

- Id: ``gof.prototype``

Use when:

- building from nothing is costly and copies differ only slightly
- the types to create are known only at run time

Avoid when:

- objects hold resources or identities that must not be shared by a copy

.. _gof.singleton:

Singleton
~~~~~~~~~

Exactly one instance of a type exists, reached through one well-known place. Prefer making it one instance by composition and injecting it, which keeps the guarantee without the global lookup.

- Id: ``gof.singleton``

Use when:

- one shared resource genuinely must have a single owner in the process

Avoid when:

- the only goal is convenient access; inject the instance instead
- tests need to replace or reset it

Structural patterns
-------------------

.. _gof.adapter:

Adapter
~~~~~~~

A thin wrapper translates one interface into the one a caller expects, so code written against its own port can use a library or service shaped differently.

- Id: ``gof.adapter``

Use when:

- an outer detail must fit an interface the inner layer owns

Avoid when:

- you control both sides and can make them agree directly

.. _gof.bridge:

Bridge
~~~~~~

An abstraction and its implementation are split into two hierarchies joined by a reference, so each can vary and grow without multiplying the classes of the other.

- Id: ``gof.bridge``

Use when:

- two independent dimensions of variation would otherwise combine

Avoid when:

- only one dimension varies

.. _gof.composite:

Composite
~~~~~~~~~

Single items and groups of items share one interface, so a tree of them is handled by callers exactly as a single item is.

- Id: ``gof.composite``

Use when:

- the domain is naturally a part-whole hierarchy

Avoid when:

- leaves and groups need operations that make no sense for the other

.. _gof.decorator:

Decorator
~~~~~~~~~

A wrapper with the same interface adds behaviour before or after delegating to the object it wraps, so responsibilities are layered on at run time without subclassing.

- Id: ``gof.decorator``

Use when:

- optional behaviours combine freely (logging, caching, retries)

Avoid when:

- the order of wrappers matters in ways callers cannot see

.. _gof.facade:

Facade
~~~~~~

One simple entry point stands in front of a subsystem with many parts, so callers depend on the few operations they need rather than on the parts.

- Id: ``gof.facade``

Use when:

- most callers use a subsystem in the same few ways

Avoid when:

- it becomes a dumping ground that every caller must change

.. _gof.flyweight:

Flyweight
~~~~~~~~~

Many fine-grained objects share their unchanging state from a common pool and keep only what differs, cutting memory when the counts are large.

- Id: ``gof.flyweight``

Use when:

- very many objects repeat the same intrinsic data

Avoid when:

- the objects are few, or their shared part is mutable

.. _gof.proxy:

Proxy
~~~~~

A stand-in with the real object's interface controls access to it: deferring its creation, checking permissions, or reaching it across a boundary.

- Id: ``gof.proxy``

Use when:

- access needs laziness, protection or remoteness the caller should not see

Avoid when:

- the hidden cost (a network call, a lock) would surprise the caller

Behavioural patterns
--------------------

.. _gof.chain-of-responsibility:

Chain of Responsibility
~~~~~~~~~~~~~~~~~~~~~~~

A request travels along a sequence of handlers until one of them deals with it, so the sender does not know which handler will answer.

- Id: ``gof.chain-of-responsibility``

Use when:

- several handlers may apply and their order is configuration

Avoid when:

- a request that nobody handles must never pass silently

.. _gof.command:

Command
~~~~~~~

An action and its arguments are captured as an object, so it can be queued, logged, retried or undone apart from whoever asked for it.

- Id: ``gof.command``

Use when:

- actions must be recorded, scheduled or reversed

Avoid when:

- a direct call would do and nothing needs the action as data

.. _gof.interpreter:

Interpreter
~~~~~~~~~~~

A small language is represented as a tree of rule objects that evaluate themselves, one class per grammar rule.

- Id: ``gof.interpreter``

Use when:

- a simple, stable grammar is evaluated often

Avoid when:

- the grammar is large or changes; use a parser instead

.. _gof.iterator:

Iterator
~~~~~~~~

Elements of a collection are visited one at a time through a uniform interface that hides how the collection is stored.

- Id: ``gof.iterator``

Use when:

- callers walk a structure without needing its internals

Avoid when:

- the language's own iteration already covers it

.. _gof.mediator:

Mediator
~~~~~~~~

Objects talk to one coordinator instead of to each other, so their interactions live in one place and each stays unaware of the rest.

- Id: ``gof.mediator``

Use when:

- many components interact in tangled, changing ways

Avoid when:

- the coordinator would absorb all the logic and become the problem

.. _gof.memento:

Memento
~~~~~~~

An object hands out an opaque snapshot of its state that it alone can restore from, so history and undo work without exposing internals.

- Id: ``gof.memento``

Use when:

- state must be rolled back and encapsulation must hold

Avoid when:

- snapshots are large and taken often

.. _gof.observer:

Observer
~~~~~~~~

Interested parties subscribe to a subject and are told when it changes, so the subject never needs to know who depends on it.

- Id: ``gof.observer``

Use when:

- one change must reach a varying set of listeners

Avoid when:

- the order or the failure of notifications matters to correctness

.. _gof.state:

State
~~~~~

An object's behaviour is delegated to a state object it swaps as it moves between states, replacing scattered checks of a status field.

- Id: ``gof.state``

Use when:

- behaviour changes with a status and the transitions are explicit

Avoid when:

- there are two states and one condition reads plainly

.. _gof.strategy:

Strategy
~~~~~~~~

A family of interchangeable algorithms sits behind one interface, and the caller is handed the one to use instead of choosing it by branching.

- Id: ``gof.strategy``

Use when:

- a behaviour varies and new variants arrive over time

Avoid when:

- there is one algorithm and no sign of a second

.. _gof.template-method:

Template Method
~~~~~~~~~~~~~~~

A base routine fixes the order of the steps and lets subclasses or supplied functions fill in particular steps.

- Id: ``gof.template-method``

Use when:

- several variants share a skeleton and differ in a few steps

Avoid when:

- the variants share little; prefer composing strategies

.. _gof.visitor:

Visitor
~~~~~~~

Operations over a fixed set of element types live in visitor objects, so a new operation is added without editing the element types.

- Id: ``gof.visitor``

Use when:

- the element types are stable and the operations keep growing

Avoid when:

- new element types are added often, since every visitor must change

Enterprise patterns
-------------------

.. _enterprise.repository:

Repository
~~~~~~~~~~

A collection-like interface, owned by the inner layer, gives access to stored domain objects, so policy reads and writes them without knowing how or where they are kept.

- Id: ``enterprise.repository``

Use when:

- domain code needs persistence it must not depend on

Avoid when:

- it would only rename the storage library's own calls one for one

.. _enterprise.unit-of-work:

Unit of Work
~~~~~~~~~~~~

The changes made during one business operation are tracked together and committed or rolled back as one, keeping storage consistent.

- Id: ``enterprise.unit-of-work``

Use when:

- one operation touches several records that must change together

Avoid when:

- each operation writes a single record

.. _enterprise.dependency-injection:

Dependency Injection
~~~~~~~~~~~~~~~~~~~~

A unit receives the collaborators it needs from outside, through its constructor or parameters, instead of creating or looking them up, and one composition root wires the whole graph.

- Id: ``enterprise.dependency-injection``

Use when:

- policy must be testable with substitutes for its details

Avoid when:

- a value has no behaviour worth replacing

.. _enterprise.service-layer:

Service Layer
~~~~~~~~~~~~~

A set of application operations forms the boundary of the use cases, coordinating domain objects and transactions so every entry point behaves the same.

- Id: ``enterprise.service-layer``

Use when:

- several entry points (command line, web, jobs) run the same operations

Avoid when:

- it holds business rules that belong in the domain objects

.. _enterprise.data-mapper:

Data Mapper
~~~~~~~~~~~

A separate mapper moves data between domain objects and the storage schema, so neither knows the shape of the other.

- Id: ``enterprise.data-mapper``

Use when:

- the domain model and the stored schema differ and evolve separately

Avoid when:

- the records are simple and map one to one

Domain patterns
---------------

.. _domain.specification:

Specification
~~~~~~~~~~~~~

A business rule about whether something qualifies is a small object that can be named, combined with others and reused for checking or selecting.

- Id: ``domain.specification``

Use when:

- the same selection or validation rule appears in several places

Avoid when:

- a single condition used once reads plainly inline

.. _domain.domain-event:

Domain Event
~~~~~~~~~~~~

Something meaningful that happened in the domain is recorded as an immutable fact, so other parts react to it without the source calling them.

- Id: ``domain.domain-event``

Use when:

- several consequences follow one occurrence and must stay decoupled

Avoid when:

- the caller needs the consequence's result immediately

.. _domain.value-object:

Value Object
~~~~~~~~~~~~

A small immutable type is defined by its values rather than an identity, carrying its own validation and operations (an amount, a range, a path).

- Id: ``domain.value-object``

Use when:

- a primitive keeps being passed around with rules attached to it

Avoid when:

- the thing has an identity that persists while its values change

.. _domain.null-object:

Null Object
~~~~~~~~~~~

A do-nothing implementation of an interface stands in for an absent collaborator, so callers need no checks for its absence.

- Id: ``domain.null-object``

Use when:

- absence has a sensible neutral behaviour

Avoid when:

- absence is an error that must be noticed
